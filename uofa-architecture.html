University of Alberta Education Architecture

Enterprise Education Middleware & Canonical Data Model

Overview

This architecture establishes a university-wide canonical education model and integration architecture for connecting academic, administrative and learning systems.

The purpose of the canonical model is to provide a consistent enterprise representation of education concepts without requiring individual source systems to adopt the same internal data model.

Architecture Principle
Systems own their operational data; the canonical model owns enterprise meaning; middleware owns integration mechanics.

The architecture therefore separates three concerns:

  • Business systems remain authoritative for the operational information they create and maintain.
  • Canonical education concepts provide a common semantic representation across systems.
  • Integration middleware performs transformation, routing, orchestration, validation and delivery.

CloudEvents is used where event-driven integration is appropriate. CloudEvents defines the event envelope and contextual metadata; it does not replace the education canonical model.

1. Architecture Vision

The architecture vision is to establish an education integration foundation that allows university systems to exchange information using stable, shared business semantics.

Business Objectives

  • Reduce point-to-point integration between education systems.
  • Establish consistent definitions for core education concepts.
  • Improve interoperability between SIS, LMS and supporting systems.
  • Provide a reusable enterprise integration model.
  • Support both API-based and event-driven integration.
  • Allow source systems to evolve without forcing consumers to understand every source-specific model.
  • Provide a foundation for future semantic and analytical capabilities.

Architecture Outcomes

Common Semantics

Education concepts such as Person, Student, Employee, Course, Course Section, Application, Admission and Enrollment have consistent enterprise meanings.

Decoupled Integration

Consumers interact with canonical representations instead of requiring direct knowledge of every source-system schema.

Event-Driven Capability

Changes can be propagated through events while preserving business semantics and contextual information.

Enterprise Governance

Canonical concepts, mappings and integration contracts become governed architecture assets.

2. Architecture Scope

The initial scope covers the core education lifecycle and the integration concepts required to connect university systems.

In Scope

  • Person and identity relationships.
  • Student and employee representations.
  • Academic programs and requirements.
  • Courses and course sections.
  • Admissions and applications.
  • Enrollment and registration.
  • Instructor and teaching relationships.
  • Canonical identifiers.
  • Source-system mappings.
  • API and event integration patterns.
  • CloudEvents event envelopes.
  • Architecture governance.
  • Future ontology and semantic-model alignment.

Out of Scope

  • Replacing the university SIS.
  • Replacing the LMS.
  • Creating a single physical enterprise database for all education data.
  • Moving operational ownership from source systems into middleware.
  • Using the canonical model as a substitute for operational application schemas.

3. Baseline Architecture

The baseline architecture recognizes that university information is distributed across multiple applications, each with its own operational data model and business responsibilities.

System Primary Responsibility Integration Consideration
PeopleSoft Student, employee, academic and administrative records. Existing enterprise source for many core institutional records.
Learning Management System Course delivery, learning activities and course shells. Requires alignment between academic sections and learning objects.
Admissions Systems Applications, admissions and applicant lifecycle. Applicant information eventually participates in the student lifecycle.
Identity Services Identity, authentication and enterprise identifiers. Provides identity context but does not become the owner of academic information.
Baseline Observation

The primary architectural problem is not simply different databases. The larger problem is that the same business concept can be represented differently by different applications.

6. Data Ownership

The canonical model does not mean that the canonical layer becomes the system of record for every concept.

Ownership remains with the application or business domain responsible for maintaining the authoritative operational state.

Concept Typical Authority Canonical Role
Person Enterprise identity / institutional system Shared representation
Student Student information system Canonical student representation
Employee HR / institutional system Canonical employee representation
Course Academic / curriculum system Canonical academic course representation
Course Section Student information system Canonical scheduled offering representation
Program Requirement Curriculum / academic governance system Canonical requirement representation
Application Admissions system Canonical application representation
Key Principle

Canonicalization standardizes meaning; it does not transfer operational ownership.

7. Integration Architecture

The integration architecture uses enterprise middleware as the mediation layer between source systems and consumers.

+-------------------+ | Source System | +-------------------+ | | Source-specific data v +---------------------------+ | Enterprise Integration | | Middleware | | | | Routing | | Transformation | | Validation | | Orchestration | | Delivery | +---------------------------+ | | Canonical representation v +---------------------------+ | Canonical Education Model | +---------------------------+ | +----------+----------+ | | | v v v Consumer A Consumer B Consumer C

Middleware Responsibilities

  • Message routing.
  • Transformation between source and canonical models.
  • Validation.
  • Schema and contract enforcement.
  • Correlation.
  • Sequencing where required.
  • Retry and delivery handling.
  • Monitoring and operational telemetry.
  • API mediation.
  • Event distribution.
What Middleware Does Not Own

Middleware should not become the business system of record simply because it performs transformation or orchestration.

8. Event Architecture

The architecture supports event-driven integration using CloudEvents as a standardized event envelope.

CloudEvents

Defines the event metadata and envelope, including event identity, source, type, subject and time.

Canonical Model

Defines the business meaning of the education information contained within the event.

Conceptual Event

CloudEvent | +-- id +-- source +-- type +-- subject +-- time +-- data | +-- Canonical Education Payload

This separation prevents CloudEvents from becoming confused with the business domain model.

Example Event Types

  • StudentCreated
  • StudentUpdated
  • CourseCreated
  • CourseSectionCreated
  • CourseSectionUpdated
  • EnrollmentCreated
  • EnrollmentUpdated
  • ApplicationSubmitted
  • AdmissionCreated

9. API Architecture

APIs provide synchronous access where consumers require current information or where an event is not the appropriate interaction pattern.

Pattern Use
REST API Request/response access to canonical resources.
Event Notification that something has changed.
Messaging Asynchronous delivery and decoupling.
Batch Large-volume or reconciliation processing.
Integration Pattern Selection

The architecture does not require every integration to use events. API, messaging, event and batch patterns are selected according to business latency, volume, consistency and operational requirements.

10. Ontology & Semantics

An ontology can provide an additional semantic layer above the canonical model where stronger formal reasoning is required.

The ontology should not replace the operational canonical model. Instead, it can formally describe concepts, relationships, classifications and constraints that require machine-interpretable semantics.

Layered Semantic Architecture

Operational Systems | v Canonical Education Model | v Semantic / Ontology Layer | +---- Concept definitions +---- Relationships +---- Classifications +---- Constraints +---- Reasoning | v Semantic Consumers

Potential Ontology Responsibilities

  • Formal definition of education concepts.
  • Classification and taxonomy.
  • Semantic relationships between concepts.
  • Equivalence or mapping between external vocabularies.
  • Validation of semantic constraints.
  • Reasoning over relationships where appropriate.
Architectural Boundary

Ontology reasoning should not become a real-time dependency for ordinary operational transactions unless there is a specific business requirement for it.

The canonical model remains the practical integration contract, while ontology provides a stronger formal semantic representation where it adds measurable value.

11. Architecture Governance

The canonical model should be governed as an enterprise architecture asset rather than as a private data structure owned by a single application team.

Governance Responsibilities

  • Approve canonical concepts.
  • Define business ownership.
  • Approve semantic changes.
  • Review new source-system mappings.
  • Manage versioning.
  • Review integration contracts.
  • Resolve semantic conflicts between systems.
  • Maintain architectural traceability.

Change Process

  1. Identify business requirement or integration need.
  2. Determine whether an existing canonical concept satisfies it.
  3. Extend the model only when required.
  4. Identify affected source and consuming systems.
  5. Update mappings and contracts.
  6. Validate backward compatibility.
  7. Approve and version the change.
  8. Deploy through controlled integration pipelines.

13. Implementation Roadmap

Implementation proceeds incrementally so that architecture decisions can be validated before broad enterprise adoption.

Phase Focus
1. Foundation Establish canonical concepts, ownership, identifiers and governance.
2. Integration Foundation Establish middleware APIs, messaging and transformation capabilities.
3. Pilot Integrate a limited number of high-value education processes.
4. Expansion Add additional systems, domains and event types.
5. Enterprise Adoption Establish the canonical model as a governed enterprise integration asset.

Implementation Principles

  • Start with high-value integration scenarios.
  • Reuse existing canonical concepts.
  • Avoid creating concepts for individual application fields.
  • Version contracts independently from application releases where possible.
  • Automate mapping and validation.
  • Maintain architecture and implementation traceability.

14. Validation

The architecture should be validated against actual university integration scenarios rather than only reviewing the conceptual model.

Validation Scenarios

  1. Create a new student and propagate the canonical student representation.
  2. Update an employee and validate identifier relationships.
  3. Create a course and course section.
  4. Assign an instructor to a course section.
  5. Register a student in a course section.
  6. Submit an application and create an admission relationship.
  7. Publish an event using the CloudEvents envelope.
  8. Consume the same canonical event in multiple downstream systems.

Validation Criteria

  • Canonical meaning is unambiguous.
  • Source ownership is preserved.
  • Mappings are deterministic.
  • Events are traceable.
  • Consumers do not require source-specific knowledge.
  • Changes can be versioned without breaking existing consumers.
  • Integration failures can be detected and reconciled.

15. Architecture Decisions

ADR-01 — Canonical Model and Data Ownership

Accepted

The canonical education model is an enterprise semantic model, not a replacement for source-system ownership.

Decision

  • Source systems remain authoritative for operational data.
  • The canonical model defines shared enterprise meaning.
  • Middleware performs integration mechanics.
  • CloudEvents provides an event envelope where appropriate.
  • Ontology can provide additional formal semantics where justified.

Rationale

A canonical model reduces semantic coupling without requiring every application to adopt the same physical database design.

This architecture also avoids making middleware an accidental system of record.

Architecture Trade-off

The architecture deliberately separates a practical integration canonical model from a more formal ontology. The canonical model is optimized for application interoperability, while ontology can be introduced where formal semantic reasoning provides additional value.

Important Architectural Distinction

CloudEvents is an event standard. It is not the education canonical model. The canonical model defines the education information carried by the event.

16. Success Measures

Success should be measured through architectural and operational outcomes rather than simply the number of integrations implemented.

Measure Desired Outcome
Canonical concept reuse New integrations reuse existing enterprise concepts where appropriate.
Point-to-point integration Reduction in direct source-to-consumer dependencies.
Data ownership Each canonical concept has an identified authoritative owner.
Integration reliability Failures, retries and reconciliation are observable and manageable.
Semantic consistency Systems use consistent definitions for shared education concepts.
Change impact Source-system changes can be absorbed through controlled mappings.
Event interoperability CloudEvents-based integrations can be consumed consistently.
Governance Canonical model changes follow an established architecture process.
End State

The University of Alberta has a governed education canonical model that provides common enterprise semantics while allowing source systems to retain operational ownership and evolve independently.

Enterprise middleware provides the integration mechanism, APIs provide synchronous access, CloudEvents supports event-driven propagation, and ontology provides an optional formal semantic layer where it delivers additional value.
